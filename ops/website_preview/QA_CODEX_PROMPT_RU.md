# Задание для Codex CLI: реальная функциональная приёмка VALYQON AI

Работай в текущем worktree `VALYQON-WEB-REVIEW` проекта `Ramzes2023/TenderLens-AI`. Сначала изучи `docs/WORKSPACE_FUNCTIONAL_ACCEPTANCE_20261024.md`, `docs/WEBSITE_BROWSER_REVIEW.md` и `ops/website_preview/compose.yaml`. Цель — **доказать или опровергнуть** работу возможностей, а не улучшить внешний вид.

## Жёсткие ограничения

1. НЕ делай merge, push, deploy, массовый запуск Worker, оплату, отправку сообщений реальным пользователям. Не меняй production, исходную базу, имена существующих Docker-volume или Compose-проекты. Для тестовых записей — **только новый изолированный disposable QA stack** с уникальным именем Compose-проекта, портами и томами; никогда не подставляй фальшивые тендеры в 18865 или main.
2. Никогда не проси пароль пользователя. Тестовые аккаунты только локальные с новым адресом `@example.test` и собственными временными данными. Письма — только локальный Mailpit. Отключи внешние источники, Telegram, платёжные шлюзы и LLM в QA-стеке.
3. Не меняй tests ради зелёного результата; если тест падает, укажи точную причину и минимальное исправление. Не объявляй синтетический источник/мок настоящим тендером.
4. Запрещено читать / копировать реальные секреты, `.env` пользователя и существующие DB volume. Не делай скриншоты с персональными адресами или токенами. Не открывай URL для авторизации из необезличенных логов.
5. Разрешены: чтение файлов/логов в worktree, запуск Git/pytest/Node/Compose для **изолированного** стека, Playwright или браузерный Chromium под QA-аккаунтом, создание redacted QA-отчёта. Все действия выполняй сейчас и фиксируй результаты, ничего не обещай «позже».

## План по шагам

A. Подтверди SHA локальной ветки и 8/8 CI по PR #264; запусти локальные contract/pytest тесты из `tests/test_authenticated_team_source_roundtrip.py`, `tests/test_tender_team_http.py`, `tests/test_tender_team_decisions.py`, `tests/test_saved_source_history.py`, `tests/test_tender_planner_ui.py`, `tests/test_team_decision_ui.py`. Если тест не запускается — укажи причину. Не меняй глобальные настройки PowerShell или другие проекты.

B. Запусти уже готовый визуальный preview скриптом `ops/website_preview/start.ps1` и реальный read-only HTTP smoke `ops/website_preview/smoke-functional.ps1`. Проверь фактические HTTP-статусы анонимных маршрутов и статические JS/CSS. Полученный JSON сохраняется в системном TEMP.

C. Для **настоящих кликов и сетевых ответов** создай одноразовый QA-контур отдельно от 18865: отдельное имя Compose, отдельные порты и тома; запрет общих volume. Для браузера используй Playwright/Chromium, если доступен. Создай локальный тестовый аккаунт, проверь регистрацию, подтверждение через локальный Mailpit, login/logout, password reset и повторный вход; никогда не отправляй email наружу. Для UI сценариев с данными используй явно помеченные `OFFLINE_FIXTURE` записи только в disposable QA DB и отражай этот уровень доказательства в отчёте.

D. Проверь каждый UI→API→DB путь с реальным браузером и обновлением страницы: создание компании, переключение, роли, сохранённые карточки; Tender Planner/канбан, PATCH этапа, конфликт двух вкладок; ручной экспорт ICS, date-only, время UTC, фильтры и числа заказчиков; назначение участника, запрос согласования, 403 самосогласования, решение другого админа, журнал; просмотр версии ЕИС из fixture и честное пустое состояние без записей. Сделай негативные проверки чужой организации и анонимных вызовов. Если какой-то пункт нельзя выполнить — пометь `BLOCKED`, не `PASS`.

E. Чётко отдели то, что НЕ проверяется из данного контура: live EIS/другие площадки, Telegram delivery, реальная Gmail/SMTP-доставка, платёжный шлюз, права по оплаченной подписке, автоматическая Google/Outlook-синхронизация, изменения содержимого PDF, официальный рейтинг конкурентов. Эти задачи требуют отдельной live приёмки на контролируемом тестовом окружении и оригинальных данных.

F. Выпусти отчёт в формате таблицы: название функции | уровень C1–C6 | выполненные действия | HTTP/DB доказательство | PASS/FAIL/BLOCKED | краткая причина. Сохрани обезличенный отчёт в `$env:TEMP\VALYQON-QA-20261024.md` и выведи абсолютный путь. Для FAIL запиши воспроизводимые шаги, файл и строку; не скрывай и не обходи ошибки. Изолированный QA-контур останови после завершения, сохрани только отчёт/обезличенные логи.

**Готовность**: только если каждому пункту есть фактическое доказательство. Проверки в CI без браузера нельзя обозначить Browser PASS. Не делай merge независимо от зелёного результата.
