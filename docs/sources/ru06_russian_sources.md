### ЕвроХим: реальная запись, но не новая независимая идентичность

Первая строка: `ШТУЦЕРА, ХОМУТЫ`, номер `4633901`, завершение
`15.10.2026 07:00`, заказчик `ЕХТР Юнит ТВО`, Волгоградская область.
Дословная ссылка:
`https://www.b2b-center.ru/app/market-next/shtutsera-khomuty/tender-4633901/`.
Остальные номера: `4632297`, `4587737`, `4581922`, `4547874`, `4558771`,
`4554815`, `4601973`, `4627288`, `4627091`. Все 10 ссылок принадлежат
`www.b2b-center.ru`; сама страница называет B2B основной торговой площадкой.

Это настоящий закупочный список на сайте заказчика, а не пустая главная.
Но источник процедуры — B2B-Center. Добавление `(ru_eurochem,4633901)`
как независимой возможности создало бы риск двойного учёта того же тендера.
Наличие этой конкретной процедуры в уже загруженной базе не проверялось.
Текущий B2B-парсер не менялся и не объявляется совместимым с этой HTML-схемой.
Возможная будущая интеграция должна сохранять discovery origin
`zakupki.eurochem.ru`, upstream `www.b2b-center.ru`, исходный номер и URL,
и согласованное правило межисточниковой идентичности. Переименование зеркала
в независимый российский источник недопустимо. Ссылка пагинации `cat_page=2`
присутствует, но следующая страница не захвачена; её контракт не подтверждён.

## Существующая инфраструктура и независимость

Изучены `TenderSource.fetch`, `TenderNotice.identity=(source, external_id)`,
`SourceRegistration`, `SourceRegistry`, `SourceCatalog`, `MultiSourceFetcher`,
bounded HTTP transport, monitoring config, worker ingestion, scoring selection,
паттерны `tests/test_ru04_sources.py` и предыдущие отчёты.
У notice цена, даты и заказчик опциональны; название, идентичность и исходная
ссылка обязательны для полезного контракта. Одних счётчиков недостаточно.

Существующие российские идентичности: `eis` — ЕИС 44-ФЗ;
`eis_223` — отдельный поток 223-ФЗ того же upstream ЕИС;
`b2b_center` — агрегированная витрина с сохранением upstream provenance;
`tektorg` — офлайн экспортная основа, не подключённый live feed.
Их нельзя считать четырьмя новыми независимыми источниками RU06.
ЕИС и B2B-зеркала регионов также требуют подтверждения происхождения,
а не предположения об уникальности по домену. Международные адаптеры
не исследовались и не менялись.

HTTP-инфраструктура уже имеет HTTPS host allowlist, ограничения запросов/байтов,
запрет автоматического redirect и защиту публичных IP/TLS/proxy; worker использует
одну существующую очередь и серверный `HOSTS`. Scoring использует существующий
allowlist `SOURCE_IDS`. Для неподтверждённых кандидатов эти списки не расширены.
Новых флагов, заглушек, каталогов, очередей, баз и сетевых движков нет.
Все 12 ID отсутствуют в каталоге и маршрутизации: они не могут включиться
по умолчанию. Defaults OFF здесь реализованы отсутствием подключения,
а не созданием фиктивного disabled-адаптера.

Для каждого успешного материала нужны полный read-only ответ, исходный и конечный

и отдельное решение о его применимости. В рамках этой задачи вход, обход CAPTCHA,
секреты и частные API не используются; закрытый доступ не объявляется connected.

После получения полноценного независимого контракта: отдельный `ru06_*.py`,
строгий host allowlist, существующий bounded transport, собственная идентичность,
дедуп, исходные ссылки и OFF по умолчанию. Тесты должны проверить отрицательные
страницы, malformed HTML, размер, spoof URL, дубли и worker integration.
Сейчас делать эти парсеры по предположенным селекторам было бы выдумкой.
